## Health Engine: incidents, verification, benchmarks, passport (directive 2, deliveries 1 and 2)

One evidence model now drives diagnosis, repair and reporting. Everything below is covered by server tests (real PostgreSQL) and agent tests; items marked *live* were also run on this Windows PC.

* **Incident lifecycle** (server): each finding becomes one incident with raw evidence, a cause, a confidence and a safe action. States follow the directive (DETECTED … RESOLVED/IMPROVED/UNRESOLVED, HARDWARE_ACTION_REQUIRED, USER_ACTION_REQUIRED, ADMIN_APPROVAL_REQUIRED). **A finished repair job never resolves anything**: it moves the incident to VERIFYING and requests a fresh health check; the symptom must be gone in a later report, then the incident is OBSERVING for its window (service 5 min, updates 30 min, storage 24 h, drivers 48 h, application crashes 7 days), and only then RESOLVED. A failed or ineffective repair escalates to a person and is not retried in a loop. A problem that returns reopens the same incident and counts the recurrence. Hardware limits are never "fixed" by software.
* **Slow-PC diagnosis**: ranked causes with the measurements behind each, confidence, and the action tied to it; states plainly when software has nothing left to fix ("software optimization limit reached").
* **Benchmark** (agent job `benchmark.run`, *live*): boot time as recorded by Windows, background CPU, memory, startup programs, running services, processes, disk write latency. Before/after comparisons report only measured differences above the noise threshold; missing values are never compared. The first measurement is the device baseline.
* **Service passport**: permanent baseline; hardware parts tracked by serial number (a replaced disk or added RAM becomes a *proposed* service event that an administrator confirms or dismisses, history is never overwritten); age is an estimate only when there is real evidence: a recorded purchase date gives HIGH; a BIOS date and a drive's power-on time are shown as weak evidence but never become an age (this PC is a 2020 laptop reporting a 2026 BIOS, which is exactly why); manual service records (type, technician, parts, serials, cost, downtime); per-device timeline "what Viro has done".
* **Stability engine** (agent collector *live*, server): every application crash and hang of the last 14 days with faulting module, exception code and versions, plus recent Windows updates and installs. One incident per unstable application; the cause is worked out from disk and memory state when each crash happened, changes just before the first crash, or a common faulting module, otherwise LOW confidence. After a repair only crashes that happened **after** it count. On this PC the collector found 28 real crash records (for example 7 crashes of an audio service) and correctly reports no automatic repair for an unsupported application.
* **One supported application repair**: Microsoft 365 / Office (Click-to-Run) Quick Repair, a controlled automatic (Level 2) recipe: fixed arguments, never closes an application (it defers and retries while Office is open), no user data touched, judged by whether the crashes stop. Unit-tested with fakes; **not yet run against the real Office on this PC** (Office 16.0.14334 is installed here).
* **Console**: care summary at the top of each computer (health, status, biggest problem, can Viro fix, hardware action), incident cards with evidence, before/after and fix buttons, "Why is this PC slow?", benchmark, passport, pending hardware changes, service history, timeline, and a "What Viro has done" card on the overview counting only verified fixes.

**Delivery 3 (built, tested):** drive condition (HEALTHY / WATCH / DEGRADED / REPLACEMENT_ADVISED / CRITICAL) from Windows health status, NVMe/SMART wear, spare capacity, uncorrectable and media errors, with rising errors between readings treated as critical and "not measured" never shown as healthy; battery condition from design versus full-charge capacity (no runtime quoted because none is measured); hardware readings are kept over time; system-drive free-space trend (growth per day and a projected date below 10 GB only when the data supports it, a cleanup starts a new segment); 7/30/90-day trends; RAM, storage and battery recommendations that state compatibility confidence, the evidence read from the computer and what could not be verified (firmware-reported slots and maximum RAM, memory type and form factor, drive interface; storage form factor is never claimed); keep / maintain / upgrade / repair / monitor / replace lifecycle decision with reasons and cost of ownership (never a remaining life, never replacement because of age alone); a fleet Lifecycle page. Covered by 6 server tests including two contrasting computers in one fleet.

**Live on this PC:** Microsoft 365 Quick Repair ran through the real agent as SYSTEM (314 s, Office 16.0.14334.20848 intact before and after, no Office application was open). Because this PC has recorded no Office crashes, this was an administrator-requested repair, not an incident-driven one, so it proves the recipe runs and verifies technically but not that a crash problem was fixed.

**Delivery 4 (fleet intelligence, built, tested):**
* **Fleet pattern detection**: the same open problem on several computers (at least 3, or 10% of the fleet) is reported with what the affected computers have in common: model, Windows build, site, department, agent version, and for crashes the application version, faulting module and cause. A shared attribute counts only when the affected computers have it much more often than the fleet as a whole (so "all run the same Windows build" is not a finding); confidence depends on that lift, with the incident's own attributes as supporting evidence only. Scattered problems are still reported, at LOW confidence, saying no shared factor stands out.
* **Staged bulk repair**: for a pattern with one common fix, the administrator starts it on **one** computer; it is repaired, and only when the problem is verified gone there (incident OBSERVING or RESOLVED, never just "the job finished") does a **pilot** (the "pilot"-tagged computers, else 10% and at least 2) get the repair, and then everyone else. With Autopilot on, a verified stage widens by itself. A repair that fails, or a pilot computer that still crashes, **halts the rollout, cancels repairs that have not started, and flags the pattern**; the rest of the fleet is never touched. Repairs postponed because an application is open are simply waited for.
* **Breakdown** by site, department, computer model and Windows version (computers, average health, computers with problems, computers needing hardware), and **KPIs** from recorded events only: verified fix rate, recurrence rate, share fixed by Autopilot, average time to healthy; a ratio with nothing to divide by is shown as "not measured", never 0.
* **Alert de-duplication**: symptoms are grouped under their root problem on a computer (crashes tied by the analysis to a full disk or memory pressure; update problems and paging that coincide with them), each marked "tied to the same cause" or "present at the same time".
* Console: a Fleet page (shared problems, staged repairs with per-computer status and Repair a pilot group / Repair everyone else / Stop, breakdown, results) and nested symptoms on a computer's page.

**Delivery 5 (Autopilot as the brain, built, tested):**
* **Policy levels** chosen by the administrator (Autopilot page): OBSERVE (diagnose and report only), SAFE (level 1: documented temporary files, stopped services, definitions updates, quick scans), BALANCED (default: adds controlled level-2 repairs: Office Quick Repair, SFC, DISM), AGGRESSIVE (adds the reversible Windows Update component repair and retries every 6 h instead of 24 h). No level ever cleans personal folders or does a broad network reset.
* **Priority order and stance**: every open problem is ranked Safety, Data protection, Stability, Security, Performance, Storage, Updates, Drivers, Preventive, and carries Autopilot's stance (working on it, will fix next, waiting for the maintenance window, watching for a return, needs hardware, needs a user, needs an administrator) with the reason. The "needs you" list (Autopilot page and weekly summary) comes from this, most important first, with the next step. A failed or ineffective repair escalates instead of looping.
* **Interruption protection**: heavy repairs (SFC, DISM, update-component repair) only start inside the maintenance window and only one at a time per computer; on the PC, disruptive repairs are **postponed, never forced** while the processor is 85% busy or the battery is low (Office Quick Repair also refuses to run while an Office application is open). A postponed repair changes nothing and is retried. Restart after a repair follows the organization's restart policy (countdown, ask, or never). Two findings that need the same repair now share one job instead of starting two.
* **Preventive incidents** from recorded history only: free space falling fast enough to fill within 14 days (Autopilot cleans safe files early), health that fell 15+ points in 14 days while now below 85, and a start-up time 50% and 20 s slower than first measured.
* **Compute obeys machine health**: Control answers each compute heartbeat with ALLOW, THROTTLE (half the CPU limit), PAUSE (a repair is running, or an application is crashing repeatedly) or BLOCK (a hardware fault); the worker applies it before its own idle, battery and temperature rules, and forgets an old instruction after 6 hours.
* Not done: detecting an active meeting or presentation (needs a per-user session probe; processor load and battery stand in for it).

Not yet built from the directive: real Windows machines other than this one (the fleet logic is proven against many simulated computers and a real database, not a real fleet), hardware readings from real failing drives (only this PC's healthy drive has been read), the OBSERVE/SAFE/BALANCED/AGGRESSIVE policy levels, meeting/presentation detection, and a controlled-VM test bed for every recipe.

## Autopilot (new: the default mode for non-technical customers)

Every new organization gets an ordinary, visible, audited policy named "Autopilot" (switch it off or change its maintenance window from the **Autopilot** console page; organizations can opt out at creation). It schedules hourly health checks, daily security posture and 12-hourly update scans, and, inside the maintenance window only, security-update installs (with the restart-after-updates countdown), weekly safe cleanup and hardware diagnosis. It fixes safe problems by itself, from an allowlist only (stopped services, safe-class cleanup, definitions update, quick scan; review-risk repairs and personal-data cleanup are never automatic), with a per-problem cooldown. Driver rollouts that an administrator starts advance test → pilot → fleet on their own, and any failed verification still halts the rollout and now also cancels installs queued on other devices. A plain-language weekly summary (PC states, what was done automatically, what needs a person) is available in the console and pushed once a week to the organization's webhooks. Covered by server tests (defaults, window gating, allowlist, cooldown, opt-out, auto-advance and halt, summary content and delivery). Not yet built: automatic *start* of driver rollouts (an administrator still picks the driver), e-mail delivery of the summary, a one-file installer per organization.

## Security incidents and the compute gate (directive 3, deliveries A and B)

* **Security incident engine (A).** `security_incidents`: a recent Microsoft Defender detection becomes an incident and moves DETECTED, CONTAINING, QUARANTINED, INVESTIGATING, REPAIR_READY, REPAIRING, VERIFYING, OBSERVING, RESOLVED (or ADMIN_ACTION_REQUIRED / UNRESOLVED). The agent's read-only `security.investigate` looks at startup entries, scheduled tasks, services in user folders, proxy, DNS, the hosts file and Defender policy. Five approved, reversible recipes (restore proxy / DNS / hosts / Defender policy, remove persistence) need an administrator's approval. Persistence is removed only when a Defender detection links to it and it is named; "unfamiliar" is never enough. Clean needs a fresh scan, a clean status read and a second inspection, then 24 hours of observation; a scan that could not run is "unverifiable", never "clean". Recurrence reopens. PCs protected by another antivirus are skipped because their detections are not visible. Covered by server and agent tests; **the investigator has not yet been run live** (the elevated run was cancelled at the UAC prompt twice), and no real detection has been walked through, because Defender is passive on this PC.
* **Compute gate (B).** Malware and ransomware incidents BLOCK compute until verified clean (PAUSE while verifying); battery stops compute by default and, where allowed, below 50% charge; heat is graded Normal / Warm (half cap) / Warning (pause) / Critical (blocked until well cooled) with hysteresis, thresholds derived from the firmware's critical temperature where readable (needs SYSTEM) and otherwise from the policy limit, and an unreadable sensor never clears a hot state. The worker reports thermal level and temperature with each heartbeat. **Not yet:** a controlled live stress test of the thermal levels (this PC's CPU zone read about 71 °C while idle-ish, so it would currently sit at Warning under the default 70 °C limit), thermal incident records, and the desktop heat popup (delivery C). A person being active still stops compute outright, which is stricter than the brief's "throttle".

## Care: heat, memory, start-up, battery, popups, outcomes (directive 3, delivery C and parts of D)

* **Safe app closing.** `ProcessClassifier` rates every program SAFE / ASK_USER / HIGH_RISK / SYSTEM_CRITICAL / UNKNOWN. Only a short approved list of background helpers with **no window and not in use** can be SAFE; Office, browsers, editors, chat and call apps are never closed automatically; unknown programs are never closed; Windows, security and remote-management software is untouchable. The rating is re-checked at the moment of closing.
* **Memory (idle programs must not hold RAM).** The care worker checks every minute; above the target (default 50%) it lets Windows take back the working set of programs that are not in use (nothing is closed, no data is lost; 15-minute cooldown per program; needs the signed-in session to be observable). The result is measured, not estimated. **Limit, stated plainly:** Viro cannot keep memory under 50% while a person is actively using the memory; on this 8 GB PC a trim reclaimed ~100 MB per pass and use stayed near 80% because of programs in use. A 4 GB PC gets an explicit "not realistic on this hardware" note.
* **Slow start-up.** Boot times come from the Windows Diagnostics-Performance log (needs the SYSTEM service). `startup.optimize` stops launchers, updaters and vendor helpers from starting with Windows (StartupApproved, reversible); security, drivers, input, audio, sync/backup and unknown items are left. The effect is measured at the next restart and shown as before/after from real boots.
* **Heat.** `ThermalMonitor` (the same graded levels as compute) raises one popup when a PC becomes hot (CLOSE SAFE IDLE APPS / VIEW DETAILS / REMIND ME), records a thermal incident with the top processes, and suspects a cooling fault only when the CPU stays hot for 15 minutes while mostly idle and Viro compute is off. After a physical cooling service the heat records before and after are compared.
* **Battery.** Real readings (capacity, health, discharge watts, cycles) every 5 minutes; `battery.diagnose` collects top processes, wake locks, power plan; the server ranks causes with evidence and measures runtime from real discharge periods only. A popup appears after 15 minutes of projected runtime under 2 hours.
* **Notices** are shown by a user-session helper with fixed text (no text or commands can be sent from Control). The storage-failing notice appears once a week per failing drive and records the backup state Windows can see (last Windows Backup, newest restore point).
* **Browser hijackers:** an extension that takes over search or the home page is reported with its evidence, and can be blocked (Chrome/Edge policy blocklist, reversible) with approval.
* **Outcomes:** home page "This month" and the Care page; per-computer "What Viro did". Every figure is a count or sum of real records; downtime avoided is not shown because it would be an estimate.
* **Release gates** (`server/test/release-gates.test.ts`) block a release if malware cannot be verified, heat does not override compute, compute runs on battery by default, risky repairs can run by themselves, a catalog recipe is untested or unimplemented, or notices can carry arbitrary text. They found four recipes that had no test; fixed.
* **Live status:** the popup was shown on a real desktop and the memory plan/trim and start-up classification ran on this PC (non-elevated). The elevated parts (boot log, backup/restore-point read, investigation, start-up optimization with rollback, battery diagnosis through the service) are scripted (`-Phase care`) but **not yet run**: the UAC prompt was dismissed.
* **Size:** the installer grew from 67 MB to 93 MB because the notice window uses Windows Forms.

## A real freeze on the development laptop, and what it taught (2026-09-30)

The PC froze and a normal restart failed (Windows logged two failed restart attempts, then a forced power-off). **Viro was not installed at the time** (no service, no care log; the last install/uninstall was hours earlier), so it neither caused nor could have prevented this. The Windows event log showed the real picture: two "low virtual memory" diagnoses (Grammarly.Desktop held 4.7 GB of commit, Chrome 3.2 GB plus 1.2 GB) on an 8 GB laptop, three security engines running at once (AVG, Malwarebytes, Defender), two firmware CPU-throttle events and two failed shutdowns.
What this exposed in the product, now fixed:
* The memory guard only looked at working sets. The freeze was **commit** exhaustion, which trimming does not relieve. The agent now reads commit, the top commit holders, and Windows' own low-memory diagnoses, and the server raises findings that name the program (`perf.low_virtual_memory`, `perf.memory_hog`), failed shutdowns, firmware throttling and overlapping security products. A popup tells the person which idle program holds the memory; Viro never closes it for them.
* The care worker's own load was reviewed against the risk of adding to a stall: thermal-zone queries are shared and cached for 15 s, the BIOS-calling ACPI thermal query is off by default, and memory trimming is limited to a few large idle programs per pass, spaced out.
* **Not solved by software:** an 8 GB laptop running a browser, a chat app and three security products will run short of memory; the lasting fix is 16 GB, and the product says so.
* Still unknown: why the restart itself hung (no shutdown-delay record was readable without administrator rights). The service reads that log once installed.

## Wake-on-LAN
- Agents report their physical adapters (hardware address, IPv4/prefix, cable or Wi-Fi, whether Windows allows wake) with each heartbeat; Control also records the address each PC reaches the internet from.
- "Wake up" (Command Center, admin): Control picks another online computer of the same organization with the SAME public address and an overlapping subnet and queues an internal `wol.send` job on it; that computer broadcasts the magic packet (UDP 9 and 7) to the target's network. Nothing is guessed: with no eligible helper the answer says why (no helper online, Wi-Fi, Windows has wake off, details not reported yet).
- `power.wol-enable` turns on "Wake on Magic Packet" in Windows (reversible). The BIOS/UEFI setting cannot be read or changed by Viro and must also allow it.
- Verified live: a helper PC on the real network received the request through production, sent the packet, and a listener on the same network captured it (102 bytes, ff*6 + target MAC x16, ports 9 and 7). Not verified: a physical PC actually powering on (needs a wired, WoL-capable PC that is switched off).
- Fixed on the way: re-enrolling a computer that had been uninstalled now clears the uninstalled flag, so it counts as a live computer again.

## Hardware Upgrade Intelligence Engine (migration 023; built and tested, not yet deployed)
Question it answers: "what hardware change can THIS computer realistically accept that will produce a measurable improvement afterwards?" Recommend -> Install -> Measure -> Prove -> Learn.
- Layers (server/src/upgrade/, one responsibility each): `normalize` (canonical CPU, board/chipset, DIMMs, drives, GPU; unknown stays null) -> `compat` (motherboard-anchored CPU pipeline: socket, chipset, board revision, BIOS, power delivery and TDP, cooling, Windows, memory type, meaningful gain, economics; first failed stage decides, all stages are recorded) -> `ram` (channel topology, mismatches, capacity only when usage justifies it, only what the board can take) -> `resolvers` (storage, cooling) -> `engine` (candidate generation, combinations, scoring, confidence, ESSENTIAL / HIGH_VALUE / OPTIONAL, replace-vs-upgrade, internal opportunity grade) -> `verify` (post-upgrade comparison) -> `fleet` (grouping, categories, bulk purchase plan). Data sources sit behind provider interfaces (`providers.ts`) so a manufacturer feed or verified outcomes can replace the built-in public tables without touching the engine.
- Anti-hallucination, enforced by tests: an OEM board's chipset is never guessed; an exact minimum BIOS version is never stated unless a provider supplied it; a processor of a different generation on an unknown chipset is "COMPATIBILITY NOT YET VERIFIED"; a processor doing >30% more sustained work than the installed one is a power-class step and is rejected on OEM boards (nominal TDP hides boost power); graphics upgrades are never offered without workload evidence (none is collected yet); predictions are ranges and say they are a model until measured; nothing under 10% gain is recommended; scoring weights never leave the server.
- Measurement: agent job `benchmark.upgrade` (CLI `viro-agent upgrade-bench`): single/multi-thread CPU, sustained load in windows with temperature and clock, memory bandwidth and latency, unbuffered drive reads from one temp file. Safety: refuses on battery, aborts at 95 C, removes its file, reports a missing temperature sensor instead of inventing one. Stored in `upgrade_benchmarks`, kept apart from the repair benchmarks.
- Proof: when a new anatomy reading shows a swapped CPU, memory, drive or board, `upgrade_verifications` records it with the prior measurement and the prediction, queues a re-measurement, and judges VERIFIED / NO_IMPROVEMENT / REGRESSION / INCONCLUSIVE with per-metric changes, temperature change, stability and "within / above / below prediction". Results are kept in `upgrade_outcomes`; once 3 verified installations agree on a board, observed results replace the model. Pooling across organizations is off unless an organization opts in (hardware facts only).
- History: `upgrade_recommendations` is immutable (UPDATE is rejected by a trigger) and gets a new row only when the advice changes.
- Console: Upgrades (fleet categories, purchase plan, identical-computer groups) and a per-computer page: your computer, do-these-first, best upgrade, other high-value, optional, worth doing together, considered-and-not-recommended, measured proof, upgrade results, and what could not be verified.
- Verified: golden machines from two REAL readings (HP 290 G4 desktop; HP ProBook 430 G7 laptop) plus labelled synthetic fixtures; 19 engine tests, 2 route tests (real DB, full recommend -> swap -> measure -> prove -> learn loop), 3 agent tests.
- NOT verified yet: the measurement has never been run to completion on a real PC (this laptop is on battery and its idle temperature is already 97 C; ZAMCOPS-GM is busy installing updates). The CPU catalogue covers Intel 6th-11th gen, Ryzen 1000-5000 and Ryzen 7000 desktop parts only; hybrid Intel parts are not modelled, so those machines get "not enough verified information". Per-board BIOS minimum versions and OEM chipsets need a provider (manufacturer data or verified outcomes). The 4-5 reference IPC ratios are rounded public figures; they are why predictions are ranges.
